# Verification Log

Every claim this project's rulesets depend on, with what was checked and why. Anything not confirmed here was not built as a primary detection — see "Confirmed gaps" below.

## claude_code

### Confirmed via official docs + live empirical testing

- **OTel enablement**: `CLAUDE_CODE_ENABLE_TELEMETRY=1`, `OTEL_LOGS_EXPORTER=otlp`, `OTEL_EXPORTER_OTLP_ENDPOINT`, `OTEL_EXPORTER_OTLP_PROTOCOL`. Source: https://code.claude.com/docs/en/monitoring-usage. Confirmed live: a real nested Claude Code CLI (v2.1.304) running in a WSL sandbox with these set produced real OTLP JSON via an OpenTelemetry Collector file exporter.
- **`tool_parameters` is documented**, not observed-only: gated by `OTEL_LOG_TOOL_DETAILS=1`, present only for Bash/MCP/Skill/Agent tools (never Read/Write/Edit). Source: https://code.claude.com/docs/en/monitoring-usage, fetched directly this session. `tool_decision`'s copy of this field is documented as showing "which command was rejected when decision is reject".
- **`permission_mode: bypassPermissions`** is the real value when `--dangerously-skip-permissions` is used. Confirmed with a real captured sample (session `363ed6e7-...`).
- **Managed-settings tampering produces a real signal even on failure**: an `Edit` targeting `/etc/claude-code/managed-settings.json` was captured with `success: "false"`, `error_type: "Error:EACCES"`, and the full attempted old/new diff in `tool_input`. The attempt itself, not success, is the detectable signal.

### Confirmed via direct empirical testing (not in official docs at this level of detail)

- **Default telemetry cannot see file paths or shell commands at all.** Without `OTEL_LOG_TOOL_DETAILS=1`, a benign read of `test.txt` and a read of `~/.ssh/id_rsa_test_fixture` produce byte-for-byte identical `tool_decision`/`tool_result` shapes except for `tool_use_id` and timestamps. This makes `OTEL_LOG_TOOL_DETAILS=1` a hard requirement for every path-based rule in this integration (997003-997007), not an optional enhancement — documented prominently in the v4.14 README rather than buried here.
- **All four disallowed-tool paths were tested; only one emits anything:**
  - CLI `--disallowedTools` flag: no `tool_decision` event. Claude Code silently used `Bash(cat ...)` instead.
  - Project `.claude/settings.json` `permissions.deny`: no event. Same Bash fallback.
  - `managed-settings.json` `permissions.deny`: no event. Same Bash fallback.
  - `PreToolUse` hook returning `permissionDecision: "deny"`: **real event**, `decision: "reject"`, `source: "hook"`. Rule 997002 is built on this path only.
  - Genuine interactive permission-prompt rejection (a human saying no at a live TTY prompt) could **not be tested**: Claude Code's interactive REPL mode forces a real OAuth browser login on first run in a fresh environment, which cannot be completed non-interactively, unlike `-p` mode which accepts `ANTHROPIC_API_KEY` directly. The docs list `user_permanent`/`user_temporary`/`user_abort`/`user_reject` as sibling `source` values to `hook` and `config`, so it is reasonable to infer this path also emits `decision: "reject"` with one of those `source` values, but this is **inferred, not confirmed**, and no rule relies on it.
- **Session transcript files** (`~/.claude/projects/**/*.jsonl`) independently record blocked attempts with more detail than OTel (`permissionDecision: {decision, source, reasonType}`, full error text), with no `OTEL_LOG_TOOL_DETAILS` flag needed. This is an **undocumented internal format** (used for `/resume`/`/rewind`, not published as a stable API), so it is noted here as an observed supplementary option, not built into the primary ruleset.

### Confirmed gaps (per the spec's own rule: list the gap, do not fake coverage, do not assign to ai_agent_host)

- The three disallowed-tool paths above that emit nothing (CLI flag, project settings deny, managed settings deny) have **no detectable signal at all**, from either Claude Code's own telemetry or the host, because nothing happens on the host either — the model simply never calls the tool. Not assigned to `ai_agent_host` per the spec's explicit instruction, since a blocked tool call produces no host activity for auditd/Sysmon/FIM to see.
- Genuine interactive permission-prompt rejection: see above. Revisit if a future session can complete a real OAuth login in the test sandbox.
- "Denied call retried via another tool", as originally scoped in the spec, does not happen the way the scenario assumes. There is no reject-then-retry; Claude Code checks tool availability before the model ever attempts the call, and silently substitutes `Bash(cat ...)` or similar from the start. The closest real signal is a `ToolSearch` tool_result immediately followed by a `Bash` tool_decision in the same session — but this pattern is also extremely common in entirely benign usage (looking something up, then doing something unrelated with Bash), so it was deliberately **not** built as a rule: the false-positive rate would be unacceptably high for a pattern this generic. No rule ships for this; documented here instead of faking a low-confidence correlation rule.
- v4.x frequency/correlation rules were not built for claude_code in this pass (no scenario in the current rule set needed one); this note exists so a future contributor doesn't assume correlation was evaluated and rejected — it simply wasn't needed yet.

### Wazuh 5.0-rc platform facts

- **No direct OTLP ingestion.** Confirmed against https://documentation.wazuh.com/5.0-rc/user-manual/capabilities/log-data-collection/how-it-works.html — Logcollector reads files via `localfile`, nothing else, for agent-side ingestion.
- **No CLI/API rule-test tool exists**, only the dashboard's manual "Log test" GUI (Ruleset management → Log test, in the Draft space, promoted through Draft → Test → Custom). Confirmed against https://documentation.wazuh.com/5.0-rc/user-manual/data-analysis/detection-workflow.html. This matches exactly what `caddy_integration_wazuh_v5.0beta`'s README already used.
- **Correlation/frequency rule-authoring syntax for the indexer's correlation engine is not documented** as of 5.0-rc (confirmed: the security-analytics module page describes `correlation_time_window` and cache tuning, but not how to author a threshold/frequency rule). No correlation-dependent scenario was built for v5.0 in this pass as a result.
- **v5.0 decoder field-access syntax for a flat key containing a literal dot is unspecified.** The docs' only dotted-path examples are for genuine nesting (`$_json.request.remote_ip`). Resolved by having the shipper scripts normalize every dotted attribute name to underscores before Wazuh ever sees it (see SCHEMA.md), rather than relying on unconfirmed bracket/quoting syntax.
- **`claude_code_wazuh_v5.0`'s decoder and all 7 rules were live-tested against a running Wazuh 5.0-rc manager/dashboard** using the Claude-in-Chrome extension (the sandboxed built-in browser tool could reach the open internet but not a local/private network address, so Chrome was used instead to reach the local dashboard). All 9 real captured sample log lines (the same samples used in `claude_code_wazuh_v4.14`'s `wazuh-logtest` validation) were run through the dashboard's Ruleset management → Log test tool, after promoting the decoder and all 7 rules from Draft to Test space. Result: 9/9 samples produced the expected rule match (or correct no-match for benign samples), matching the v4.14 `.ini` expected-rule mapping exactly, including the two-rule match on the download-and-execute-under-bypass sample (997001 + 997004 both fire). Rules 997001-997004 fire with full originally-scoped detection logic; rules 997006 and 997007 were deliberately narrowed from their original scope — see "Confirmed Wazuh 5.0-rc engine defects" immediately below.
- **Platform architecture facts confirmed empirically during live testing:**
  - A space's root decoder (the one with no `parents:`) is enforced at promotion time — promoting a decoder that has `parents:` set but whose named parent doesn't already exist/promoted in that space fails with "The root decoder '...' cannot have parents". `decoder/claude-code/0`'s parent is the platform's own `decoder/core-wazuh-message/0`, which performs `parse_json($event.original)` into `_tmp_json` — every custom decoder in a space ultimately chains from it.
  - A `check:` expression does not support property-chaining off a helper function's return value (e.g. `string_equal(parse_json($event.original).service_name, "x")` fails to parse: "Single quote expected"). A helper function's result must be assigned to a field in a `map:` step first, then referenced as `$field.subfield` in a later step.
  - This same two-step pattern was required for `tool_parameters`: it arrives as a JSON-encoded string, so `process.command_line` must be populated via an intermediate `_tmp_tool_params: parse_json($_tmp_json.tool_parameters)` map step before extracting `$_tmp_tool_params.full_command` — confirmed as a genuine decoder correctness fix (not a test-only artifact): without it, `process.command_line` held the entire raw JSON blob instead of just the shell command text, which would have silently broken every regex rule matching against it (997003, 997004) in production.
  - **A decoder's `map:` target field names are validated against Wazuh's built-in Wazuh Common Schema (WCS) at promotion time, not freely definable.** Attempting to add `session.id: $_tmp_json.session_id` to the decoder (to carry the agent's session identifier into a normalized field, for future cross-agent correlation) was rejected at save time with: `Field 'session.id' is not defined in WCS schema and is not a temporary field (root must start with '_')`. Every other field this decoder maps to (`event.kind`, `event.dataset`, `service.type`, `user.id`, `message`, `process.name`, `event.id`, `event.action`, `event.outcome`, `event.provider`, `tags`, `file.path`, `process.command_line`, `error.message`) validated successfully, confirming these are real WCS-defined fields and `session.id` specifically is not one of them. This was reverted rather than worked around (e.g. by inventing a non-standard field name), since doing so would misrepresent the decoder as having a WCS-compliant field it does not. The agent session identifier is therefore **not currently mapped into any normalized v5.0 field** — a confirmed gap, see SCHEMA.md's note on the v5.0 column. No rule in this integration depends on session correlation, so this does not block any of the 7 scenarios, but it does mean `claude_code_wazuh_v5.0` cannot yet support session-scoped or cross-agent-session correlation that `ai_agent_host` might eventually want to build on.

### Confirmed Wazuh 5.0-rc `|re:` regex engine defects (empirically isolated via repeated Log Test runs)

The following constructs were observed to silently prevent an otherwise-correct `|re:` pattern from matching, confirmed by toggling each construct in isolation against the same sample line and re-running Log Test:

- `\s` and `\b` (backslash shorthand character classes) do not reliably match. Worked around by using explicit bracket classes instead (e.g. `\s+` → `[ ]+`).
- `(?i)` (inline case-insensitive flag) breaks matching entirely when present. Removed from every rule; all patterns in this integration match only the casing observed in real captured samples.
- `\.` (escaped literal dot) is unreliable. Worked around by using an unescaped `.` (functions as "match any character" — an acceptable, intentionally overbroad substitute) or avoiding the dot entirely.
- A regex pattern consisting of a single top-level `(...)` group wrapping the ENTIRE expression fails outright (e.g. `(id_rsa)` alone does not match, but `id_rsa` with no wrapping group does). Flat alternation or a group that does not span the whole pattern is unaffected.
- The literal `/` character breaks matching in some observed contexts: `tmp` alone matches, but `/tmp/` does not, isolated by testing both patterns against the identical sample and detection block. Root cause not identified (possibly related to escaping/serialization of the folded YAML block scalar the dashboard uses for long field values, but this was not conclusively isolated).

None of the above are documented in the official 5.0-rc docs as of this session; they are empirical findings from this testing session only and should be re-verified against future Wazuh 5.0 GA releases, since they may be rc-specific bugs rather than permanent engine behavior.

### Confirmed gap: narrowed scope for rules 997006 and 997007 (per the spec's mandatory-verification rule — documented here rather than fabricated as full coverage)

- **Rule 997006 (credential access)** was originally scoped to match any of: `.ssh/`, `.aws/credentials`, `.kube/config`, `.npmrc`, `.git-credentials`, `id_rsa`, `id_ed25519`, `.env`. Multiple regex structures were attempted to express this as a single working `|re:` pattern — flat alternation (`a|b|c|...`), the same alternation wrapped in one outer group, and a multi-named-detection-block boolean-OR structure (`condition: selection and (ssh_path or aws_path or kube_path or ...)`) — all failed to fire in Log Test despite the live rule content being independently re-confirmed correct via the rule's JSON view after each promotion. The shipped rule is narrowed to the single pattern confirmed working in isolation: `id_rsa`. Broader credential-path coverage is **not implemented** and is a known, documented gap, not a fabricated capability.
- **Rule 997007 (scope-escape write)** was originally scoped to match `/tmp/`, `/etc/`, `/var/`, or `/root/` via `"file_path":"(/tmp/|/etc/|/var/|/root/)`. This failed in Log Test; isolating the failure down to the bare path segment showed `tmp` alone matches but `/tmp/` (with slashes) does not. The shipped rule is narrowed to the bare segment `tmp`, which is intentionally broader/fuzzier than the original slash-delimited intent (it would also match a path merely containing the substring "tmp" anywhere, not only `/tmp/`) but is the only form confirmed to actually fire. Coverage of `/etc/`, `/var/`, `/root/` is **not implemented** and is a known, documented gap.
